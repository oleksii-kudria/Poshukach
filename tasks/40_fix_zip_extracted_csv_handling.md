# TASK-040: Виправити обробку CSV, витягнутих із ZIP-архівів

## Контекст

У задачі `39_zip_dhcp_archives.md` було додано підтримку ZIP-архівів у:

`data/raw/dhcp`

Після merge задачі 39 у `main` під час запуску:

```bash
python3 scripts/psh.py
```

виявлено помилку під час обробки CSV, витягнутого з ZIP:

```text
❌ Виявлено помилки структури CSV у data/raw/.dhcp-zip-8m25ci1i/2026-08-20-data_export.csv_1__2026-08-20-data_export.csv
Файл порожній або не містить заголовок.

Зупинка обробки.
```

При цьому оригінальний CSV усередині архіву містить дані та коректний заголовок.

Приклад заголовка реального CSV:

```text
Log Source Time,Log Source Identifier,Source MAC,Payload
```

Отже, проблема виникає не у вихідному CSV, а на етапі підготовки / копіювання тимчасового CSV із ZIP до стандартного pipeline.

---

## Мета

Виправити ZIP-input layer так, щоб CSV-файли після вилучення з архіву гарантовано передавалися у стандартний CSV pipeline з повним вмістом.

Існуючу логіку парсингу звичайних `.csv` файлів змінювати не потрібно.

---

## Що потрібно зробити

### 1. Перевірити механізм extraction

Перевірити поточну реалізацію у ZIP input layer і з'ясувати, чому після розпакування може створюватися тимчасовий CSV, який `read_csv_header()` визначає як порожній.

Необхідно гарантувати, що:

- вміст entry повністю прочитаний із ZIP;
- весь вміст записаний у temporary file;
- файл закритий / flush завершений до передачі у `read_csv_header()`;
- у стандартний pipeline передається правильний шлях до фактично записаного файлу;
- не створюються зайві порожні destination-файли.

---

### 2. Перевіряти витягнутий CSV після запису

Після extraction необхідно перевіряти файл перед додаванням до списку вхідних CSV.

Мінімальна перевірка:

- файл існує;
- розмір більше `0` байт.

Бажано також перевірити, що файл містить хоча б один непорожній рядок.

Порожній або некоректно витягнутий CSV не повинен передаватися у стандартний CSV pipeline.

---

### 3. Не зупиняти весь pipeline через проблемний CSV із ZIP

Якщо конкретний CSV усередині ZIP:

- порожній;
- не читається;
- пошкоджений;
- не вдалося повністю витягнути;

необхідно:

- вивести warning;
- вказати назву ZIP та ім'я entry;
- пропустити цей CSV;
- продовжити обробку інших CSV у цьому та інших ZIP-архівах.

Наприклад:

```text
⚠️ Пропущено CSV "folder/file.csv" з ZIP "archive.zip": файл порожній після extraction
```

ZIP input layer не повинен передавати завідомо невалідний temporary file у `run_dhcp_aggregation()`.

---

## Важливе обмеження

Не змінювати загальну поведінку для звичайних файлів:

```text
data/raw/dhcp/*.csv
```

Якщо звичайний CSV без ZIP має невалідну структуру, чинна поведінка pipeline може залишатися без змін.

Новий skip-on-error у цій задачі стосується саме помилок, які виникають на рівні ZIP extraction / temporary CSV preparation.

---

## Regression case

Додати тест із CSV, який має такий header:

```text
Log Source Time,Log Source Identifier,Source MAC,Payload
```

CSV повинен містити реальні рядки DHCP payload у тому самому форматі, який вже підтримує поточний parser.

Тестовий сценарій:

```text
data/raw/dhcp/archive.zip
└── 2026-08-20-data_export.csv
```

Після запуску aggregation:

- CSV повинен успішно витягнутися;
- `read_csv_header()` повинен отримати реальний header;
- файл не повинен визначатися як порожній;
- записи повинні пройти існуючий DHCP pipeline.

---

## Додаткові тести

### Test case 1: валідний CSV у ZIP

ZIP містить один CSV із даними.

Очікується:

- temporary file має розмір більше 0;
- CSV успішно обробляється.

### Test case 2: порожній CSV у ZIP

ZIP містить:

```text
empty.csv
valid.csv
```

Очікується:

- `empty.csv` пропускається з warning;
- `valid.csv` обробляється;
- pipeline не завершується аварійно.

### Test case 3: декілька ZIP

```text
archive1.zip -> valid1.csv
archive2.zip -> empty.csv
archive3.zip -> valid2.csv
```

Очікується:

- `valid1.csv` та `valid2.csv` обробляються;
- `empty.csv` пропускається;
- один проблемний entry не блокує інші архіви.

### Test case 4: ім'я архіву / CSV з додатковими крапками та suffix

Наприклад:

```text
2026-08-20-data_export.csv_1.zip
└── 2026-08-20-data_export.csv
```

Очікується:

- generated temporary filename коректний;
- файл не перезаписується;
- файл має повний вміст;
- aggregation проходить успішно.

### Test case 5: однакові імена CSV

```text
archive1.zip -> data.csv
archive2.zip -> data.csv
```

Очікується:

- обидва temporary files мають унікальні імена;
- обидва містять правильний вміст;
- жоден файл не перезаписує інший.

---

## Логування

Додати зрозумілі повідомлення для ZIP input layer.

При успішному extraction бажано мати можливість побачити:

```text
🔧 ZIP archive.zip: extracted CSV folder/data.csv
```

Для помилки:

```text
⚠️ ZIP archive.zip: CSV folder/data.csv пропущено - файл порожній після extraction
```

Не потрібно виводити весь payload у лог лише для діагностики extraction.

---

## Зворотна сумісність

Після виправлення мають продовжувати працювати:

- прямі `.csv` у `data/raw/dhcp`;
- декілька `.zip` архівів;
- CSV у вкладених директоріях ZIP;
- однакові імена CSV у різних ZIP;
- `.CSV` / `.ZIP` незалежно від регістру;
- FortiGate;
- MikroTik;
- CEF;
- dnsmasq;
- UniFi;
- усі інші поточні DHCP формати.

Не змінювати parser logic без прямої необхідності.

---

## Очікуваний результат

Після виправлення валідний CSV із ZIP більше не повинен викликати:

```text
Файл порожній або не містить заголовок.
```

якщо оригінальний entry реально містить дані.

ZIP input layer повинен гарантувати, що тільки повністю записані та непорожні temporary CSV передаються у стандартний pipeline.

---

## Критерії приймання

Задача вважається виконаною, якщо:

1. Валідний CSV із ZIP зберігає весь вміст після extraction.
2. `read_csv_header()` коректно читає header із temporary CSV.
3. CSV із header `Log Source Time,Log Source Identifier,Source MAC,Payload` успішно проходить ZIP pipeline.
4. Порожній CSV усередині ZIP пропускається до передачі у parser.
5. Один проблемний CSV із ZIP не зупиняє обробку інших CSV/ZIP.
6. Унікалізація імен temporary CSV не призводить до порожніх або перезаписаних файлів.
7. Додані regression tests для описаного production case.
8. Існуюча логіка прямих `.csv` не змінена.
9. Усі попередні тести задачі 39 продовжують проходити.
10. Усі інші тести проєкту проходять без регресій.
