# TASK-039: Додати підтримку ZIP-архівів у `data/raw/dhcp`

## Контекст

У директорії:

`data/raw/dhcp`

зараз обробляються `.csv` файли з DHCP / network event logs.

Існуючу логіку роботи з `.csv` файлами потрібно **залишити без змін**.

Необхідно додати підтримку `.zip` архівів, які можуть містити один або декілька `.csv` файлів.

---

## Що потрібно зробити

Додати можливість розміщувати у директорії:

`data/raw/dhcp`

будь-яку кількість `.zip` архівів.

Кожен ZIP-архів може містити:
- один `.csv` файл;
- декілька `.csv` файлів;
- додаткові файли інших типів;
- вкладені директорії.

Під час обробки необхідно витягувати з ZIP-архівів **тільки `.csv` файли**.

Всі інші типи файлів потрібно ігнорувати.

---

## Основна вимога

Після отримання `.csv` файлів із ZIP-архівів подальша логіка роботи скрипту повинна залишитися такою самою, як для звичайних `.csv` файлів, які вже знаходяться у:

`data/raw/dhcp`

Тобто не потрібно дублювати або створювати окрему логіку парсингу для файлів із ZIP.

ZIP має бути лише додатковим способом доставки `.csv` файлів у стандартний pipeline.

---

## Підтримувані вхідні файли

Після реалізації у `data/raw/dhcp` можуть одночасно знаходитися:

```text
data/raw/dhcp/file1.csv
data/raw/dhcp/file2.csv
data/raw/dhcp/archive1.zip
data/raw/dhcp/archive2.zip
data/raw/dhcp/archive3.zip
```

Всі звичайні `.csv` файли повинні оброблятися як і раніше.

Всі `.zip` архіви повинні бути додатково опрацьовані.

---

## Обробка ZIP-архівів

Для кожного `.zip` файлу необхідно:

1. Відкрити архів.
2. Переглянути його вміст.
3. Витягнути тільки файли з розширенням `.csv`.
4. Файли інших типів ігнорувати.
5. Передати отримані `.csv` у вже існуючу логіку обробки.

Приклад:

```text
archive.zip
├── dhcp.csv
├── events.csv
├── readme.txt
├── image.png
└── logs/
    └── dhcp2.csv
```

Повинні бути оброблені:

```text
dhcp.csv
events.csv
logs/dhcp2.csv
```

Повинні бути проігноровані:

```text
readme.txt
image.png
```

---

## Конфлікти імен файлів

Необхідно врахувати, що різні ZIP-архіви можуть містити `.csv` файли з однаковими назвами.

Наприклад:

```text
archive1.zip
└── dhcp.csv

archive2.zip
└── dhcp.csv
```

Не можна допустити, щоб один файл перезаписав інший.

Під час підготовки файлів до обробки необхідно забезпечити унікальне ім'я для кожного витягнутого `.csv`.

Рекомендований підхід:

```text
<archive_name>__<original_csv_name>
```

Наприклад:

```text
archive1__dhcp.csv
archive2__dhcp.csv
```

Для CSV у вкладених директоріях також потрібно уникати конфліктів.

Наприклад:

```text
archive1.zip -> logs/dhcp.csv
archive1.zip -> backup/dhcp.csv
```

Обидва файли повинні отримати різні імена.

Допускається:
- додавання назви архіву як префікса;
- додавання шляху всередині архіву у нормалізованому вигляді;
- генерація унікального suffix / UUID.

Але бажано використовувати **детерміноване та зрозуміле ім'я**, щоб при діагностиці можна було визначити, з якого ZIP походив файл.

---

## Тимчасові файли

Якщо для роботи існуючого pipeline потрібно фізично витягувати `.csv` на диск, їх слід розміщувати у тимчасовій директорії.

Не потрібно розпаковувати CSV назад безпосередньо у:

`data/raw/dhcp`

щоб:
- не змішувати вхідні файли з тимчасовими;
- не створювати повторну обробку на наступному запуску;
- не залишати сміття у `data/raw/dhcp`;
- уникати конфліктів імен.

Після завершення роботи тимчасові файли повинні бути очищені.

Якщо існуюча архітектура дозволяє передавати CSV із ZIP без фізичного розпакування, можна використати такий підхід, але він не повинен вимагати зміни логіки парсингу CSV.

---

## Поведінка при помилках

Пошкоджений або невалідний ZIP-архів не повинен зупиняти обробку інших файлів.

Необхідно:
- записати warning / error у лог;
- вказати ім'я ZIP-файлу;
- перейти до наступного файлу.

Так само помилка читання одного `.csv` всередині ZIP не повинна блокувати обробку інших `.csv` з цього або інших архівів, якщо поточна архітектура це дозволяє.

---

## Безпека розпакування

Необхідно врахувати ZIP path traversal / Zip Slip.

Архів не повинен мати можливості записати файл за межі дозволеної тимчасової директорії через конструкції типу:

```text
../../some-file.csv
```

Не використовувати небезпечне сліпе розпакування всього архіву.

Потрібно працювати тільки з валідними `.csv` entries та контролювати шлях призначення.

---

## Регістр розширень

Бажано підтримати `.csv` незалежно від регістру:

```text
.csv
.CSV
.Csv
```

Аналогічно для ZIP:

```text
.zip
.ZIP
```

якщо це не суперечить існуючій логіці проєкту.

---

## Зворотна сумісність

Критична вимога:

**існуюча логіка обробки `.csv` файлів не повинна змінитися.**

Після реалізації:

```text
data/raw/dhcp/*.csv
```

повинні працювати так само, як до цієї задачі.

ZIP-файли повинні лише додатково надавати `.csv` для того самого pipeline.

Не змінювати без необхідності:
- парсери DHCP;
- логіку normalize;
- diff;
- report;
- визначення форматів CSV;
- FortiGate parser;
- MikroTik parser;
- dnsmasq parser;
- UniFi parser;
- інші вже підтримувані джерела.

---

## `.gitignore`

Необхідно додати правило, щоб ZIP-архіви з директорії:

`data/raw/dhcp`

не потрапляли у Git-репозиторій.

Наприклад:

```gitignore
data/raw/dhcp/**/*.zip
data/raw/dhcp/*.zip
```

Або використати еквівалентне правило відповідно до поточної структури `.gitignore`.

Якщо підтримується case-insensitive pattern у поточному підході - врахувати також `.ZIP`.

При цьому не зламати існуючі винятки для:

```text
*.example.csv
```

## Критерії приймання

Задача вважається виконаною, якщо:

1. У `data/raw/dhcp` можна розмістити будь-яку кількість `.zip` архівів.
2. З кожного ZIP обробляються тільки `.csv` файли.
3. Інші файли з ZIP ігноруються.
4. CSV у вкладених директоріях архіву також підтримуються.
5. Однакові назви `.csv` у різних ZIP не призводять до перезапису.
6. Однакові назви `.csv` всередині одного ZIP не призводять до перезапису.
7. Після отримання CSV використовується існуюча логіка обробки без дублювання parser logic.
8. Звичайні `.csv` у `data/raw/dhcp` продовжують працювати без змін.
9. Пошкоджений ZIP не зупиняє обробку інших файлів.
10. Реалізація захищена від Zip Slip.
11. Додані відповідні автоматичні тести.
12. У `.gitignore` додано правило для ZIP-архівів у `data/raw/dhcp`.
13. Існуючі тести проєкту продовжують проходити.
