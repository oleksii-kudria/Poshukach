# TASK-038: Розширити парсер FortiGate DHCP ACK для полів без лапок і довільного порядку

## Контекст

У задачі `37_fortigate_dhcp_parser.md` було додано підтримку журналів подій FortiGate DHCP ACK у файлах:

`data/raw/dhcp/*.csv`

Після запуску обробки журналів з іншого обладнання FortiGate виявлено новий варіант формату `payloadAsUTF`, який поточний парсер не може розпізнати.

Повідомлення про помилку:

```text
⚠️ Неможливо розпарсити рядок payloadAsUTF: <FortiGate payload>
```

Ймовірна причина полягає в тому, що деякі значення у FortiGate payload можуть передаватися без подвійних лапок. Зокрема, поле `ip` у новому форматі має вигляд:

```text
ip=192.0.2.117
```

замість раніше підтримуваного:

```text
ip="192.0.2.117"
```

Також порядок полів у payload може відрізнятися, а `devname` і `devid` можуть розташовуватися наприкінці рядка.

---

## Анонімізований приклад нового формату

```text
<190>reporting_ip=203.0.113.10 logver=700190696 timestamp=1784799358 date=2026-07-23 time=12:35:58 eventtime=1784799358701506800 tz="+0300" logid="0100026001" type="event" subtype="system" level="information" vd="root" logdesc="DHCP Ack log" interface="internal" dhcp_msg="Ack" mac="AA:BB:CC:DD:EE:FF" ip=192.0.2.117 lease=604800 hostname="N/A" msg="DHCP server sends a DHCPACK" devname="FG-60F-EXAMPLE" devid="FGT60FXXXXXXXXX"
```

У прикладі навмисно замінено реальні:
- зовнішню IP-адресу;
- внутрішню IP-адресу пристрою;
- MAC-адресу;
- назву FortiGate;
- серійний номер / device ID.

---

## Що потрібно зробити

Розширити універсальний парсер FortiGate DHCP ACK так, щоб він коректно обробляв значення у форматах:

```text
key="value"
```

і:

```text
key=value
```

Парсер не повинен залежати від:
- наявності лапок навколо значення;
- фіксованого порядку полів;
- позиції `devname`, `devid`, `mac`, `ip` або `hostname` у payload;
- наявності додаткових полів, яких не було в попередніх прикладах.

---

## Обов'язкові поля для вилучення

Для DHCP ACK події потрібно отримати:

- `mac` - MAC-адресу клієнтського пристрою;
- `ip` - IP-адресу клієнтського пристрою;
- `hostname` - hostname клієнтського пристрою;
- сирий `payloadAsUTF`.

Додаткові поля FortiGate, зокрема `reporting_ip`, `devname`, `devid`, `interface`, `lease`, можуть бути збережені, якщо вони вже передбачені внутрішньою моделлю, але не повинні впливати на успішність базового парсингу DHCP-події.

---

## Правила розпізнавання FortiGate DHCP ACK

Рядок слід вважати FortiGate DHCP ACK, якщо payload містить ознаки:

```text
logdesc="DHCP Ack log"
```

та/або:

```text
dhcp_msg="Ack"
```

і містить поля `mac` та `ip`.

Порядок цих полів не повинен мати значення.

---

## Вимоги до парсингу key-value

Реалізувати або розширити універсальний key-value parser, який підтримує:

### Значення у подвійних лапках

```text
mac="AA:BB:CC:DD:EE:FF"
hostname="Example Device"
msg="DHCP server sends a DHCPACK"
```

### Значення без лапок

```text
ip=192.0.2.117
lease=604800
timestamp=1784799358
reporting_ip=203.0.113.10
```

### Значення з пробілами

Значення з пробілами повинні коректно читатися, якщо вони взяті в лапки:

```text
hostname="Example Device"
logdesc="DHCP Ack log"
```

### Довільний порядок полів

Обидва варіанти повинні оброблятися однаково:

```text
mac="AA:BB:CC:DD:EE:FF" ip=192.0.2.117 hostname="Example"
```

```text
hostname="Example" devname="FG-EXAMPLE" ip=192.0.2.117 mac="AA:BB:CC:DD:EE:FF"
```

---

## Обробка hostname

У новому прикладі FortiGate повертає:

```text
hostname="N/A"
```

Потрібно застосувати чинні правила нормалізації проєкту.

Якщо в проєкті значення `N/A`, порожній рядок або відсутній hostname вважаються відсутнім ім'ям, нормалізувати його до:

```text
unknown
```

Не створювати окрему несумісну логіку тільки для FortiGate.

---

## Обробка MAC

MAC-адреса повинна:
- витягуватися незалежно від позиції у payload;
- нормалізуватися до формату `XX:XX:XX:XX:XX:XX`;
- проходити чинну валідацію MAC;
- не спричиняти падіння всього pipeline у разі невалідного значення.

---

## Обробка IP

Поле `ip` повинно підтримувати обидва формати:

```text
ip="192.0.2.117"
```

```text
ip=192.0.2.117
```

Необхідно:
- вилучити тільки значення IP;
- не захоплювати наступне поле `lease`;
- виконати чинну валідацію IP;
- не плутати клієнтський `ip` з полем `reporting_ip`.

Клієнтська адреса пристрою береться саме з ключа:

```text
ip
```

Поле:

```text
reporting_ip
```

є окремим службовим полем FortiGate і не повинно замінювати IP клієнтського пристрою.

---

## Зворотна сумісність

Після змін мають продовжувати працювати:
- попередній формат FortiGate із `ip="..."`;
- FortiGate CSV з названою колонкою `payloadAsUTF`;
- FortiGate CSV з payload-колонкою без назви;
- усі раніше підтримувані MikroTik, CEF, dnsmasq, UniFi та інші DHCP формати.

Необхідно уникати регулярного виразу, жорстко прив'язаного до конкретного порядку полів.

---

## Логування помилок

Якщо FortiGate payload не вдалося розпарсити:
- не завершувати обробку всього файлу аварійно;
- записати зрозуміле попередження;
- за можливості вказати, які обов'язкові поля не знайдено;
- не виводити зайві чутливі дані у production-логах, якщо у проєкті вже передбачено маскування.

---

## Тести

Додати або оновити автоматичні тести.

### Test case 1: IP у лапках

```text
mac="AA:BB:CC:DD:EE:FF" ip="192.0.2.117" hostname="Example"
```

Очікується:
- MAC: `AA:BB:CC:DD:EE:FF`
- IP: `192.0.2.117`
- name: `Example`

### Test case 2: IP без лапок

```text
mac="AA:BB:CC:DD:EE:FF" ip=192.0.2.117 lease=604800 hostname="Example"
```

Очікується:
- MAC: `AA:BB:CC:DD:EE:FF`
- IP: `192.0.2.117`
- lease не потрапляє в IP
- name: `Example`

### Test case 3: hostname N/A

```text
mac="AA:BB:CC:DD:EE:FF" ip=192.0.2.117 hostname="N/A"
```

Очікується:
- запис успішно оброблений;
- hostname нормалізований відповідно до чинних правил, бажано до `unknown`.

### Test case 4: довільний порядок

```text
hostname="Example" reporting_ip=203.0.113.10 devname="FG-EXAMPLE" ip=192.0.2.117 mac="AA:BB:CC:DD:EE:FF"
```

Очікується:
- клієнтський IP: `192.0.2.117`;
- `reporting_ip` не використовується як IP пристрою;
- MAC і hostname визначені коректно.

### Test case 5: повний анонімізований payload

Використати повний приклад із цієї задачі як test fixture.

---

## Очікуваний результат

Після реалізації наведений FortiGate DHCP ACK payload повинен успішно оброблятися без повідомлення:

```text
⚠️ Неможливо розпарсити рядок payloadAsUTF
```

Нормалізований запис повинен містити щонайменше:

```text
mac=AA:BB:CC:DD:EE:FF
ip=192.0.2.117
name=unknown
```

Після цього запис має пройти стандартний pipeline:

```text
validate -> collect -> normalize -> diff -> report
```

---

## Критерії приймання

Задача вважається виконаною, якщо:

1. FortiGate payload з `ip` без лапок успішно парситься.
2. FortiGate payload з `ip` у лапках продовжує працювати.
3. Парсер не залежить від порядку key-value полів.
4. Поле `reporting_ip` не плутається з клієнтським `ip`.
5. `mac`, `ip` і `hostname` вилучаються коректно.
6. `hostname="N/A"` обробляється відповідно до чинної нормалізації.
7. Додані тести для обох форматів IP та довільного порядку полів.
8. Усі попередні тести проєкту проходять без помилок.
9. Підтримка інших DHCP джерел не зламана.
